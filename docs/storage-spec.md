# Спецификация: тома, объекты, монтирования

Статус: **Object утверждён, остальное черновик и обсуждается по порядку** (Размещение, Volume, Монтирование, слой игрока). Кода нет. Прода нет, схема меняется без совместимости.

## 1. Зачем

1. Один механизм для файлов машины и записей вики.
2. Убрать обходы: служебные машины под файлы, поддельные файлы-хранилища (`/.keystore`, `/.sigstore`, `/.slices`), `delivered_only`, адреса `url`.
3. Системные образы по типу машины и отличия конкретной машины поверх.
4. Общее состояние через удалённое монтирование.
5. Основа для прав, политик-конфигов, `edt`, приложений-файлов.

Вне этой спецификации: права, политики, `edt`, логи, hex.

## 2. Модель

```
Machine ──< MachineMount >── Volume ──< Placement >── Object
```

- **Object** самостоятельный: не привязан ни к тому, ни к машине. Это база файлов.
- **Volume** хранит дерево размещений.
- **Placement** (рабочее имя) положил объект в том: так один объект лежит в нескольких томах без дубликатов.
- **MachineMount** подключает том к машине.

### 2.1 Object (утверждено)

| Группа | Поля |
|---|---|
| Основное | `slug` (уникальный, обязательный; заменяет `direct_link` и слаги ассета/карты/письма), `name`, `format` |
| Содержимое | зависит от формата, см. ниже |
| Доступ | `access` (условие по слагам объектов-ключей), подписи и встроенные ключи (выбор среди объектов) |
| Внутренности | `state` (базовые слои; размещение в томе может заменить или отключить) |
| Метаданные | `size` (если не указан, считается по содержимому, кнопка refresh), `meta` (свободный текст/разметка, универсальный контейнер для любого файла, заменяет `infobox`), `world_created_at`, `world_updated_at`, `world_creator` |
| Админское | `created_*`, `updated_*`, ревизии, блокировка |

**Содержимое по формату.** В реестре форматов (`FileFormat`) появляется настройка «источник содержимого», по ней форма объекта показывает нужные поля:

| Формат | Содержимое |
|---|---|
| текст | `body`, либо выбор документа-текста среди ассетов |
| картинка | поле для ссылки (в том числе внешний URL) и пикер ассетов (то же окно, что в ассетах, из Nextcloud) |
| видео, звук | пикер ассетов |
| документ | пикер ассетов |
| `exe` и подобные | `body` либо ассет |
| ключ | `body` (пусто: генерируется из слага) |
| карта | пикер сцены карты |
| письмо | пикер письма |
| без содержимого | пусто; размер задаётся `size`, байты генерируются |

- **Внешний URL:** окно показывает адрес, а байты файла генерируются (`size` из поля), с сети ничего не качается.
- **Карта и письмо** остаются записями своих приложений; объект формата `map`/`msg` ссылается на запись, байты строятся из неё.
- **Ключ** это объект формата ключ; `secure.Key` (только `slug`, `description`, даты) поглощается им. Условия доступа, подписи и встроенные ключи выбирают среди таких объектов.

**Не на объекте:** `editable`, `visibility`, `system`, права и путь живут в размещении и монтировании.

**Исчезает:** `MachineFile.url`, `delivered_only`, `Document.storage_class`, `Namespace.node`, `visibility` у `Namespace` и `Document` (заменено флагом `hidden` у размещения), `direct_link` (становится `slug`), надгробие как объект.

Ревизии и блокировка (`ItemRevision`, `ItemLock`, `ImportBatch`) переезжают с `Document` на объект.

### 2.2 Размещение (утверждено в основном)

Строка дерева тома. Папки отдельные строки (у них свои условия доступа и пустую папку иначе не создать).

| Поле | Смысл |
|---|---|
| `volume`, `parent` | том и родитель (пусто = корень тома) |
| `kind` | `folder`, `object`, `whiteout` |
| `name` | необязательное имя в этом месте; по умолчанию имя объекта + расширение формата |
| `object` | у `folder` и `whiteout` пусто |
| `hidden` | флаг «скрыт» |
| `access_mode` + `access` | `inherit` / `replace` / `none`; текст условия виден только при `replace` |
| `state_mode` + `state` | то же для слоёв: как у объекта / заменить / нет |
| `system` | защищён от удаления игроком (до введения прав) |

Позже: владелец, группа, режим.

**Скрытие.** Файл скрыт, если у размещения `hidden` **или** имя начинается с точки; правило одно для всех машин (терминал единый). Скрытое не показывает `ls` без `-a`; вики не показывает его в списках и поиске, но открывает по ссылке. Это соглашение о показе, а не защита (защита это `access`). Условной видимости по ключам (`visibility` у `Namespace` и `Document`) больше нет. Отдельного переключателя «показать скрытые» в вики нет: показ определяют политики хоста и то, как игрок подключён к вики (файл приложения).

**Доступ.** Условия папок вдоль пути складываются, как в вики сейчас (закрытую папку не открыть). Условие файла берётся из размещения при `replace`, из объекта при `inherit`, при `none` файл открыт (папки вдоль пути всё равно действуют).

**Слои.** `inherit` берёт `state` объекта, `replace` заменяет текстом размещения, `none` отключает слои в этом месте. Прогресс игрока (`PlayerFile.state`) считается от действующих слоёв.

Уникально `(volume, parent, имя в этом месте)`. Глубина папок до 16 (у вики сейчас 4).

### 2.3 Volume (на обсуждении)

| Поле | Смысл |
|---|---|
| `name` | **мир игры:** как диск называется (проводник Windows, `df`, `mount`, `vol`); необязательное и не обязательно уникальное. Пусто: Windows-подобная машина показывает `Local Disk (C:)`, Unix-подобная `uuid` |
| `uuid` | **мир игры:** идентификатор для `fstab`/`df`; создаётся сам, автор может задать свой |
| `label` | **админка:** метка для автора, по ней том ищут в списках; игрок её не видит |
| `slug` | **движок:** идентификатор тома (уникальный, латиница) для админки, импорта, тестов; в мире игры не появляется |
| `access` | условие по ключам, закрывающее весь том |

**Два пространства имён.** Всё, что игрок читает (`fstab`, файл приложения вики, `df`), называет тома по-игровому: `uuid`, `name`, а для сетевого тома пара «хост и имя экспорта» (`archive-srv:/harbor`). Имя экспорта задаёт хост на своём local-монтировании (поле `export`, пусто = том наружу не отдаётся). Слаг в игровом тексте не используется.

**Приватный том машины** не имеет особого вида: это том, смонтированный на одну машину как корень. Он создаётся вместе с машиной (шаблон), а при удалении машины его убирает действие в админке. Полей `kind` и `machine` у тома нет: они выводятся из монтирований.

**Правила имён тома** (регистр, запрещённые символы) пока не моделируются; позже добавятся необязательными полями.

### 2.4 Монтирование (на обсуждении)

| Поле | Смысл |
|---|---|
| `machine` | кто монтирует |
| `volume` | какой том |
| `volume_path` | папка внутри тома, которая монтируется (пусто = корень тома) |
| `mount_path` | куда монтируется на машине (в том числе диск `C:`); пусто = в файловую систему не попадает |
| `mode` | `local` или `remote` |
| `order` | порядок слоёв, если на одну точку смонтировано несколько томов |

**Как работает `order`.** Если на одной точке лежит один том, порядок не нужен. Если томов несколько, они складываются стопкой, и `order` говорит, какой выше: больший перекрывает меньший. Пример: на `/` у машины системный том `aether-base` (`order 0`, нижний) и её собственный том с отличиями (`order 1`, верхний). Файл верхнего тома перекрывает одноимённый файл нижнего, надгробие верхнего скрывает файл нижнего.

**Хост remote определяется сам:** это единственная машина, у которой этот том смонтирован `local`. Если том не смонтирован `local` нигде, он внешний: один общий экземпляр для всех, кто его подключил `remote`. Если `local`-машин несколько, `remote` на такой том запрещён (непонятно, к какому подключаться). В игровых текстах сетевой том называется парой «адрес хоста и имя тома» (`archive-srv:/harbor`), отдельного имени экспорта нет.

Проверки: два монтирования на одну точку только с разным `order`; у каждой машины есть корневое монтирование; `remote` на том с несколькими `local`-хозяевами запрещён.

**Windows-подобные машины.** Точка монтирования может быть диском (`C:`), внутри хранится как `/C:` (двоеточие в именах объектов запрещено, столкновений нет). У такой машины корневое монтирование это диск, а `/` служит виртуальным корнем, который перечисляет диски. На `Machine` добавляется `path_style` (`unix` / `windows`): **диалект путей**, вид на границе терминала. Внутри пути канонические; машина показывает и принимает их по-своему (`C:\Users\ivan`, обратные слэши) в приглашении, `pwd`, `ls`, сообщениях и аргументах команд. Хранение от диалекта не зависит. Шаблон «новая машина Aether» создаёт приватный том и два монтирования на `/`: системный (`order 0`) и приватный (`order 1`).

### 2.5 Экземпляр и слой игрока (утверждено)

`VolumeInstance(volume, host)`: `local` на машине M даёт `(том, M)`; `remote` указывает на экземпляр хоста, который определяется из монтирований (см. 2.4): `(том, H)` или, если том внешний, `(том, пусто)`.

**Слой игрока** это личные отличия игрока от общей базы. Каждая запись `PlayerFile` (бывший `SessionFile`) описывает одно отличие по одному пути. Уникально `(user, instance, path)`.

| Поле | Смысл |
|---|---|
| `user`, `instance` | чей слой и над каким экземпляром |
| `path` | путь **внутри тома** (один том может лежать в разных местах разных машин) |
| `object` | на какой объект указывает запись (может лежать в другом томе) |
| `data` | собственные байты записи, только для вырезки (произвольные байты в текст не уложить) |
| `content` | текст: у записи с `object` своя версия его тела (правка `edt`), `NULL` = не правили; у записи **без** `object` это и есть содержимое файла (например, подпись) |
| `state` | прогресс по слоям защиты |
| `deleted_at` | надгробие: файл удалён игроком |
| `origin_path`, `trashed_at`, `purge_at` | корзина |

Правило: у записи может быть `object` или собственное содержимое (`content` для текста, `data` для байтов), но не то и другое сразу.

**Файлы, которые создают команды.** Новое содержимое создают только `blk` и `ward sign`:
- **Подпись** (`ward sign`) это новый файл игрока без объекта: блок подписи (текст, определяется парой «ключ, хеш») записывается прямо в `content`. Формат определяется по самому тексту; запись читается, копируется и переносится как любой файл.
- **Вырезка** (`blk`) это слепок байтов в `data`, как у `dd`: источник потом меняться может, файл остаётся таким, каким был создан. Вырезка делается по одному разу на каждое действие игрока и содержит произвольные байты, поэтому в библиотеку объектов не идёт. Лимит `data`: 1 МБ, при превышении `blk: output too large`. `xfer` переносит байты как любой файл. Формат определяется по самим байтам; `edt` для таких файлов текстовую правку не включает (правка байтов появится вместе с hex-редактором).
- Остальные команды (`cp`, `mv`, `cvt`, `pak x`, `xfer`, сохранение вложения, `rcvr`) создают запись со ссылкой на тот же объект; `kex` ссылку на объект-ключ в `secrets`.

Из схемы уходят виды источников `slice` и `signature`, таблица `FileSlice`, адреса `sig/...`, `/.slices`, `/.sigstore`. `FileSignature` (подписи, встроенные автором в объект) остаётся.

`Session(user, profile)` остаётся для входа, `ttl`, блокировок, файлов в нём нет. `Attachment.machine_file` → `Attachment.object`.

### 2.6 Тип системы и именованные места

`Machine.system` из списка в коде становится записью в БД (**тип системы**: Aether, Apollo, Eden, Windows-подобная и т.д.). На ней: `path_style` (диалект путей, 2.4) и набор **именованных мест**.

**Место** это имя и шаблон пути: `Place(system или machine, name, path)`. Значения типа системы задают умолчание, машина может переопределить. Порядок разрешения: машина, затем тип системы, затем умолчание в коде. Движок не знает путей, он спрашивает место по имени.

| Имя | Что | Пример (Unix) | Пример (Windows) |
|---|---|---|---|
| `home` | домашняя папка записи | `/home/{login}` | `C:\Users\{login}` |
| `secrets` | ключи записи | `{home}/.secrets` | `{home}\.keys` |
| `desktop` | рабочий стол записи | `{home}/Desktop` | `{home}\Desktop` |
| `trash` | корзина записи | `{home}/.trash` | `C:\$Recycle.Bin\{login}` |
| `config` | конфиги политик (`access.conf`, `exports`, `fstab`, `limits.conf`, `sudoers`) | `/etc/aether` | `C:\ProgramData\Aether` |
| `logs` | логи | `/var/log` | `C:\Windows\Logs` |
| `temp` | временные файлы | `/tmp` | `C:\Temp` |

- **Переменные:** `{login}` (логин записи) и `{home}` (место `home`). Место с переменной у каждой записи своё (у `ivan` и `admin` разные ключи, стол и корзина), остальные общие для машины.
- **Расширяемость:** код объявляет известные имена и умолчания (реестр в Python), автор может добавить свои имена на тип системы или машину; движок неизвестные имена не использует, но на них можно ссылаться из слоёв, хуков и сцен.
- **Папка может не существовать** в томе: создаётся при первом использовании.
- **Ключи.** Ключи, которые игрок держит на машине, это объекты формата ключ в папке `secrets` его записи в виде машины, **откуда бы они туда ни попали, в том числе из смонтированного удалённого тома**. Том, смонтированный (в том числе `remote`) на папку `secrets`, выдаёт игроку все ключи, которые в нём лежат, и пока том смонтирован и доступен, ключи действуют; отмонтировал или связь оборвалась, ключи пропали. Константа `/home/.secrets` уходит из кода; `kex`, вложения писем и подписи пишут в `secrets` текущей записи.
- **Рабочий стол** показывает всё содержимое места `desktop` записи (кроме скрытого): приложение запускается, любой другой файл открывается по своему формату. Заменяет `MachineApp` (фаза 4).
- Пути в мест хранятся в каноническом виде (`/C:/Users/...`); админка принимает их в диалекте системы.

## 3. Как собирается вид машины

Для игрока P на машине M:
1. Монтирования сортируются по глубине точки, затем по `order`.
2. По очереди: **затенение** (глубокая точка скрывает всё под собой), **объединение** (та же точка: записи ложатся поверх), объекты тома в пределах `subpath` ложатся под точкой, `whiteout` удаляет запись, одноимённая запись верхнего слоя перекрывает нижнюю.
3. После каждого слоя применяется слой P над его экземпляром: надгробия, правки, копии, новые файлы.
4. У каждой записи вида запоминается слой, откуда она пришла.

**Куда пишет игрок:** новый файл в верхний записываемый слой, покрывающий путь; правка или удаление существующего в слой, откуда пришла запись (копия вверх); перенос между томами это надгробие и новая запись.

## 4. Remote

- Remote использует тот же экземпляр, что local у хоста: действия игрока видны на обеих машинах (если позволяют права). Синхронизации нет, состояние одно.
- Два local одного тома это два независимых экземпляра.
- Содержимое тома общее: правка автора видна на всех экземплярах, пока игрок не перекрыл запись.
- Игроки состояния друг друга не видят.
- Недоступный хост даёт `Stale file handle`, том исчезает из вида. Первая версия: хост всегда доступен; позже `ttl`, маршрут, политики.
- Идентификация на хосте по учётным данным монтирования (фаза 5).

## 5. Вики

Вики это приложение, а не том: оно подключает тома и само называет их разделы. Том о вики ничего не знает. Страницы вики это размещения объектов формата, умеющего быть страницей (`FileFormat.page`), в подключённых томах.

- **Целевая схема (фаза 4):** тома и названия разделов задаёт файл приложения (`volume archive-srv:harbor as Harbor`); адрес `apps/wiki/<Название раздела>/<Папка>/.../<Название>`.
- **До фазы 4 (временно):** вики показывает те тома машины, где есть страницы (объекты формата `page`); раздел называется по `name` тома, иначе по `slug`.
- `go/<slug>` проверяет, что объект есть в подключённом томе. Ключи, видимость, ревизии, блокировки, поиск работают как раньше. Один объект открывается и как файл (`cnt`), и как страница.

Редактор и предпросмотр в админке объекта строятся на редакторе вики; разметка зависит от формата.

## 6. Источники

Реестр `filesystem/sources` остаётся и выбирает класс по формату/содержимому объекта, а не по префиксу адреса. `Address` и разбор адресов исчезают. Источники: текст, ассет, внешняя ссылка, сцена карты, письмо, ключ, без содержимого, плюс собственные байты записи игрока (`data`).

## 7. Затрагиваемый код

Около 60 файлов: модели и миграции (`filesystem`, `wiki`, `machines`, `mail`, `secure`), вид файловой системы (`terminal/engine/filesystem.py`, `fileops.py`, `trash.py`, `transfer.py`, `filesystem/session_ops.py`), команды терминала, слои и ключи (`filesystem/states/*`, `unlock.py`, `keystore.py`, `slices.py`, `size.py`, `content.py`, `sources/*`), вики, почта, админки, рабочий стол (пока `MachineApp` без изменений). Упоминаний: `MachineFile` в 25 файлах, `SessionFile` в 23, `Document` в 27, `Namespace` в 24.

## 8. Данные

Прода нет, база разработки **пересоздаётся с нуля**: конвертера нет. Миграции всех затронутых приложений переписываются заново (чистые `0001`), контент набирается заново в новой админке. В конце фазы 1 в репозитории остаётся команда создания демонстрационных данных (машина, тома, объекты, монтирования) для проверки руками и тестов.

## 9. Фазы

Каждая заканчивается зелёными тестами и замером числа запросов.

1. **Тома и объекты:** `Volume`, `Object`, `Placement`, `PlayerFile`, local-монтирование на `/`, вид файловой системы из монтирований, вики на новых моделях, почта и ключи на объектах, форма объекта по формату с пикерами. Бюджет запросов: `ls -l` не растёт вместе с числом файлов.
2. **Слои:** несколько монтирований, объединение и затенение, надгробия, `volume_path`, шаблон машины, админка с собранным деревом.
3. **Remote и экземпляры.**
4. **Приложения-файлы:** файл вики с синтаксисом томов, рабочий стол из `~/Desktop`, удаление `MachineApp` и `VolumeMount`.
5. **Права, политики, `edt`.**

## 10. Риски

- Объём фазы 1: порядок внутри фазы (модели → вид → команды → вики → почта) с прогоном тестов после каждого блока.
- Пути внутри тома против путей на машине: нужны тесты переноса между слоями.
- Изменение нижнего слоя, перекрытого верхним, невидимо; зафиксировать тестом.
- Вырезка файла с правкой игрока: слепок берётся из того, что игрок видит сейчас, поэтому правка попадает в вырезку.
- Кириллица и пробелы в именах в терминале: нужны кавычки (разбор через `shlex`).
- Вики 6.7 тысяч строк, замена механическая, но широкая.
